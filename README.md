# Hospital Data Assistant Agent

A multi-agent text-to-SQL assistant built with Google's **Agent Development Kit (ADK)** and **Gemini**.
Ask questions about hospital operations in plain English: a coordinator routes each question to a
specialist, the analyst writes SQL, a reviewer agent checks it, and the query runs read-only before
the result is explained. Concept questions go to a tutor agent that teaches with the same tables.

> All data is **synthetic** and generated by `setup_db.py`. No real patient information is used.

## Example

```
You:   Which department had the highest average charge for inpatient visits?
Agent: my_agent → data_analyst
       (get_database_schema → sql_reviewer: APPROVED → run_sql_query)
       SELECT d.name, ROUND(AVG(v.total_charge), 2) AS avg_charge
       FROM visits v JOIN departments d ON v.department_id = d.department_id
       WHERE v.visit_type = 'Inpatient'
       GROUP BY d.name ORDER BY avg_charge DESC LIMIT 1;
       → Oncology has the highest average inpatient charge ...
```

## How it works

### Agent team

```
                 my_agent (coordinator)
                 /                    \
       data_analyst                  sql_tutor
            |
   sql_reviewer (agent-as-tool)
```

| Agent | Role | Tools |
|---|---|---|
| `my_agent` | Routes each message to the right specialist. Answers nothing itself. | none (transfers only) |
| `data_analyst` | Writes SQL, sends it for review, runs it, explains the result, handles follow-ups | all data tools + `sql_reviewer` |
| `sql_reviewer` | Checks the SQL against the question and schema; replies `APPROVED` or `REVISE` | `get_database_schema` |
| `sql_tutor` | Explains SQL and data engineering concepts using the hospital tables | `get_database_schema`, `explain_query` |

Two ADK multi-agent patterns are used:

- **Transfer (`sub_agents`)**: the coordinator hands the conversation to `data_analyst` or
  `sql_tutor`, which then talks to the user directly. Follow-up questions stay with the
  agent that is already handling the conversation, so the coordinator is not called again.
- **Agent-as-tool (`AgentTool`)**: the analyst calls `sql_reviewer` like a function and gets
  its verdict back. The reviewer only sees the question and SQL it is sent, never the user
  conversation, so its review is independent.

Only `data_analyst` can run queries. Instructions for every agent are in
[`app/prompts.py`](app/prompts.py); the wiring is in [`app/agent.py`](app/agent.py).

### Tools

| Tool | Purpose |
|---|---|
| `get_database_schema` | Tables, columns, join keys, row counts and allowed values for categorical columns |
| `run_sql_query` | Runs a single read-only `SELECT` and returns up to 50 rows |
| `explain_query` | Shows the SQLite query plan without running the query |
| `get_query_history` | Returns the last 5 successful queries in this conversation |
| `set_answer_format` | Saves whether the user prefers tables or plain-text answers |

Tools live in [`app/tools.py`](app/tools.py).

**Guardrails**
- Only a single `SELECT` / `WITH` statement per call; anything else is rejected
- The database is opened read-only (`mode=ro`), so no query can change data, even if validation were bypassed
- Queries are stopped after 5 seconds (protects against accidental cross joins)
- Results are capped at 50 rows; the agent is told when results were truncated
- Gemini API calls retry up to 5 times with exponential backoff (2s, 4s, 8s, 16s) on 429/503 errors
- SQL errors come back with a hint (e.g. "check the schema") so the agent can fix its own query

**Session state (follow-up questions)**

The agent keeps a small notepad in ADK session state:

| Key | Scope | Purpose |
|---|---|---|
| `last_query` | This conversation | The last successful SQL, injected into the instruction so follow-ups like *"same for Radiology"* or *"now by month"* modify it |
| `query_history` | This conversation | The last 5 successful queries |
| `user:answer_format` | All of this user's conversations | `table` or `text`; the `user:` prefix makes it outlive a single session |

Tools write state through ADK's `ToolContext`; the instruction reads it with
`{last_query?}` and `{user:answer_format?}` placeholders. Open the **State** tab
in the playground to watch it change.

```
You:   Average inpatient charge by department?
Agent: (runs SQL, saves it as last_query)
You:   Only for 2026.
Agent: (adds a visit_date filter to last_query and re-runs it)
```

**Tests**

```bash
uv run pytest tests/unit
```

28 unit tests run without any LLM calls: the tools (schema output, query results, row caps, every guardrail,
session-state updates) and the agent wiring (routing structure, which agents can run queries,
valid state placeholders in every prompt).

## Data model

```
departments (department_id, name, floor)
doctors     (doctor_id, first_name, last_name, department_id, hire_date)
patients    (patient_id, first_name, last_name, birth_date, gender, city, insurance_type)
visits      (visit_id, patient_id, doctor_id, department_id, visit_date,
             visit_type, diagnosis, total_charge)
```

8 departments · 24 doctors · 300 patients · 1,500 visits (Jan 2025 – Sep 2026)

## Run it locally

**Prerequisites:** Python 3.11+, [uv](https://docs.astral.sh/uv/), Node.js 18+,
and a free Gemini API key from [Google AI Studio](https://aistudio.google.com).

```bash
# 1. Install agents-cli
uvx google-agents-cli setup

# 2. Clone and install
git clone https://github.com/nandaReddy1212/hospital-data-agent
cd hospital-data-agent
agents-cli install

# 3. Add your API key
echo "GOOGLE_GENAI_USE_VERTEXAI=False" > .env
echo "GEMINI_API_KEY=your-key-here" >> .env

# 4. Build the synthetic database
python setup_db.py

# 5. Start the playground
agents-cli playground
```

Open the local URL it prints and try questions like:
- "How many visits did each department have?"
- "Who are the top 5 patients by total charges?"
- "What is the most common diagnosis in Cardiology?"
